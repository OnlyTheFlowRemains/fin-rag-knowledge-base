# 踩坑记录（真实开发过程中遇到并修掉的问题）

> 这份文档最有面试价值。面试官问"你踩过什么坑"，背不出来的人只能说"没什么坑"，
> 而这四个坑都是**跑出来的数字暴露的**，不是想出来的。

---

## 坑 1：chunk 丢失文档级上下文（本项目最大的一次质量提升）

### 现象

问「泓远沪深300增强ETF 的托管费年费率是多少」，召回回来的是"产品基本信息"段落，
**根本没召回到"费用结构"段落**，答案里没有 0.10%。

### 原因

「费用结构」这一段的原文是：

```
管理费按前一日基金资产净值的 0.50% 年费率计提……托管费年费率为 0.10%。
```

**这段话里一次都没出现基金名字。** 而问题里带着"泓远沪深300增强ETF"，
所以带名字的段落（产品基本信息、免责声明）把召回名额全占了。
这是 RAG 的经典缺陷：**切块之后，每个块都失去了"我属于哪篇文档的哪一节"这个信息。**

### 修法：contextual chunk header（上下文标题前缀）

索引时给每个块拼一个头部，**只用于检索，不给模型看**：

```python
@property
def index_text(self) -> str:
    header = "泓远沪深300增强ETF 2024年度产品说明 · 费用结构"
    return f"{header}\n{self.text}"
```

embedding 和 BM25 都改成吃 `index_text`，而喂给大模型的 `context` 保持原文干净。

### 效果（真实测出来的，不是估的）

3 个费率类问题：

| 方案 | 正确段落排第一 | 答案里有正确数字 |
|---|---|---|
| 带 header | 3/3 | 3/3 |
| 不带 header | 1/3 | 1/3 |

在完整的 11 条评估用例上（`scripts/eval.py`），同集对比：

| 方案 | hit_rate | MRR | ctx_precision |
|---|---|---|---|
| 带 header | 1.000 | 0.944 | **0.861** |
| 不带 header | 1.000 | 0.944 | **0.750** |

注意 hit_rate 和 MRR 没变——因为它们是**文档级**归属，召回到同一篇文档的任意段落都算命中。
header 的收益体现在**段落级精度**上，这也说明**指标选得不对就看不见改进**。

**最关键的一条**：不带 header 时，问 A 基金的申购费率，召回回来的是 **B 基金**的费用段。
在金融场景里，"自信地答错产品"比"答不出来"严重得多。

这个消融实验写成了测试（`test_without_header_fee_queries_hit_the_wrong_section_or_fund`），
所以 README 里那张表不会随代码变动而变成假话。

### 面试怎么讲

> "我做 RAG 时发现一类问题召不回：问某只基金的费率，费率段落里不重复基金名，
> 而问题里有基金名，结果带名字的段落把召回位占满了。我的解法是 contextual chunk header——
> 索引时把文档标题和小节名拼在块前面，但喂给模型的还是干净原文。
> 3 个费率问题从 1/3 提到 3/3。更重要的是，改之前有一个问题召回到了另一只基金的费用段，
> 那种错在金融场景是不能接受的。"

## 坑 2：doc_id 拼接把文件名切坏，导致评估指标全错

### 现象

评估跑出 `hit_rate=0.500`，但人工看召回结果明显是对的。

### 原因

我给每个小节生成 id 用了 `f"{doc_id}-s{sec_idx}"`，评估时再用 `doc_id.split("-s")[0]` 还原。
但语料文件名本身带 `-s`：

```
"fund-bond-stable-s2".split("-s")[0]  →  "fund-bond"   # 错！应该是 fund-bond-stable
"compliance-suitability-s1".split("-s")[0]  →  "compliance"
```

于是"召回的文档"和"期望的文档"永远对不上，指标假低。

### 修法

分隔符换成不可能出现在文件名里的 `::`：

```python
doc_id = f"{doc.doc_id}::s{sec_idx}"     # fund-bond-stable::s2
_doc_root = lambda d: d.split("::")[0]
```

### 教训

**指标异常时，先怀疑指标本身算错了，别急着调模型参数。**
我当时差点去调 chunk_size 和 top_k——那样调一天也没用，因为召回本来就是对的。

## 坑 3：LLM provider 挂掉会把整个请求打成 500

### 现象

写了个测试模拟"provider 挂了"，结果整个 `graph.invoke()` 直接抛异常。

### 原因

HyDE 那一步我写了 try/except 兜底，但 generate 节点没写。线上表现就是：
模型 API 超时或限流 → 用户看到 500 → 已经检索到的资料全丢了。

### 修法

generate 节点捕获异常，降级返回"生成服务暂时不可用 + 检索到的来源"，
并在 `reasons` 里记 `generation-error:TimeoutError`，`trace` 里记 `generate:failed`。

```python
try:
    raw = self.llm.complete(prompt)
except Exception as exc:
    return {"answer": GENERATION_FAILED_MESSAGE, "citations": citations, ...}
```

### 面试怎么讲

> "Agent 服务里外部依赖（模型 API）是最不可靠的一环，超时和限流是常态不是异常。
> 我的处理原则是**降级而不是报错**：生成失败了，检索到的来源还是有价值的，
> 直接把来源返回给用户，让他自己查原文，同时在响应的 trace 字段里标记失败原因，方便排查。"

## 坑 4：Mock LLM 不看召回排名，把别的基金的数字拼进答案

### 现象

问沪深300ETF 的管理费（正确答案 0.50%），答案里混进了 `管理费年费率为 0.30%`——
那是纯债基金的费率。

### 原因

Mock LLM 挑句子时只按"关键词命中数"排序，**完全不管这句话来自第 [1] 块还是第 [4] 块**。
召回排序其实是对的（来源[1] 就是正确的费用结构段），是"生成"这一步没有尊重排名。

### 修法

按块的排名加权：`权重 = 1 / (1 + 0.35 × 块序号)`，越靠前的块权重越高。
真实 LLM 也是这样——你把 `[1] [2] [3]` 编号给它，它会更信前面的。

### 更普适的教训

**召回对 ≠ 答案对。** 两只产品结构高度相似的文档放在一个知识库里，
"答错产品"是一类独立的失败模式，必须单独写测试盯住
（`test_answer_quotes_the_asked_about_fund_not_a_neighbour`）。

## 坑 5（未修，属于已知局限，要能坦白说）

**HyDE 在当前离线配置下测不出收益。** 消融跑出来四档指标一模一样：

```
baseline (hyde+rerank)  hit_rate=1.000 mrr=0.944 ctx_precision=0.861
no hyde                 hit_rate=1.000 mrr=0.944 ctx_precision=0.861
```

原因：mock LLM 生成的"假设性答案"本身就是从同一批语料里抄句子拼的，
没有引入任何新的查询信号。HyDE 的收益要接真实大模型才能体现。

**面试千万别吹成"我用 HyDE 提升了 X%"**——一追问怎么测的就露馅。正确说法是：

> "HyDE 我实现了，但在我的离线评估里测不出收益，因为 mock provider 的假设性答案
> 来自同一批语料，没有新信息。这个我在 README 里写明了。要真验证得接真实模型跑一遍。"

**这样答比吹一个数字加分**——说明你知道什么叫"有对照的实验"。
