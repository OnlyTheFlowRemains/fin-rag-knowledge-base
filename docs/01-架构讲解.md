## 一、这个项目到底在解决什么问题

一句话：**让大模型基于金融文档回答问题，且答案可追溯、不越合规红线、外部服务挂了也不崩。**

拆成三层理解：

1. **RAG 层**（技术核心）：文档切块 → 向量化 → 检索 → 塞进 prompt → 生成。
2. **合规层**（金融特色）：不许答"该不该买"，不许预测价格，不许执行下单。
3. **工程层**（能上线）：FastAPI 接口、SSE 流式、降级、可观测（trace）、评估指标。

面试时如果只讲第 1 层，你和所有跟过教程的人一样。**第 2、3 层才是区分度。**

## 二、为什么用 LangGraph 而不是 LangChain 的链

对应文件：`fin_rag/graph.py`

**链（Chain）是一条直线，图（Graph）能分叉。** 这个流程真的需要分叉：

| 情况 | 需要的行为 |
|---|---|
| 用户说"帮我下单" | **跳过检索直接拒答**（检索是浪费，也没意义） |
| 检索分数都低于阈值 | **跳过生成直接拒答**（否则模型会编） |
| 正常问题 | 走完整流程 |

用链实现这些分支，只能在函数里写一堆 `if...return`，流程藏在代码里看不见。
用图，分支是**声明式**的：

```python
graph.add_conditional_edges(
    "compliance", self._route_compliance, {"refuse": "refuse", "expand": "expand"}
)
graph.add_conditional_edges(
    "rerank", self._route_hits, {"generate": "generate", "refuse": "refuse"}
)
```

好处有三个，都能拿出来讲：

1. **每条路径可以单独测**。测"合规拒答不走检索"就断言 trace 里没有 `retrieve:`。
2. **状态可见**。`RagState` 是一个 TypedDict，每个节点只管往里加字段。
3. **能加 checkpoint/人工审核**。LangGraph 支持在节点间持久化状态、中断等人工确认，
   这是企业级 Agent 的刚需（比如金融场景要"人工复核后再发出"）。

### 六个节点分别干什么

| 节点 | 文件位置 | 职责 |
|---|---|---|
| `compliance` | `compliance.py` | 判断问题是否越界，产出 verdict |
| `expand` | `rerank.py:hyde_expand` | 用 LLM 生成假设性答案，扩充检索信号 |
| `retrieve` | `retrieval.py` | 向量 + BM25 双路召回，RRF 融合 |
| `rerank` | `rerank.py` | 重排，截断到 top_k，过滤低分 |
| `generate` | `graph.py` | 拼 prompt、调模型、清洗输出 |
| `refuse` | `graph.py` | 两种拒答（合规拒答 / 无资料拒答） |

## 三、检索为什么要"双路 + RRF"

对应文件：`fin_rag/retrieval.py`

### 两路各自的强项和盲区

| 方式 | 原理 | 强在哪 | 盲在哪 |
|---|---|---|---|
| 向量检索（dense） | 语义相似度 | 换个说法也能找到（"回撤"↔"下跌幅度"） | **精确标识符会被模糊掉**（基金代码 519301、2024Q3） |
| BM25（sparse） | 词频统计 | 精确匹配、代码/数字/术语 | 换个说法就找不到 |

金融问题里两种成分都很多——"519502 的最大回撤"既有代码又有术语。所以**必须两路都要**。

### 为什么用 RRF 融合而不是把分数相加

这是很容易被追问的点。答案：**两路的分数不在一个量纲上。**

- 余弦相似度：范围 `[-1, 1]`，有界。
- BM25 分数：**无界**，跟词频、文档长度、idf 都有关，可以是 3 也可以是 30。

直接相加，BM25 会因为数值大而支配结果，这不是因为它更准，纯粹是量纲问题。

RRF（Reciprocal Rank Fusion）只看**排名**不看分数：

```python
score = Σ  weight / (k + rank + 1)
```

`k=60` 是原论文的经验值。k 小了会过度偏向第一名，k 大了各名次差异被抹平。

**我额外做的一点**：HyDE 生成的查询权重设 0.5，用户原问题权重 1.0。
理由——不能让模型编出来的假设性答案盖过用户真正问的东西。
这条也写了测试（`test_rrf_downweights_expansion_queries`）：塞一个完全无关的扩展查询进去，
原本的第一名不能被挤掉。

### BM25 为什么自己手写

`rank_bm25` 装一下就有，但我手写了 30 行。原因是**面试会问 BM25 公式**，
自己写过才讲得清 `k1`（词频饱和）、`b`（长度归一化）、`idf` 的 `+0.5` 平滑是干什么的。
装库你只会用，不会讲。

### 中文分词为什么用字符二元组而不是 jieba

代码里 `ngrams()` 把中文切成 2 字滑窗（"最大回撤" → 最大/大回/回撤）。

- 少一个依赖，纯 Python 实现。
- **对金融术语和未登录词更稳**——jieba 的词典未必有"沪深300增强"、"HyDE"这种词，切错了检索就废了。
- 字符 bigram 是中文信息检索公认的强基线。

代价：语义泛化能力不如真正的分词 + 语义模型。所以留了 `EMBEDDING_PROVIDER=sentence-transformers` 的口子。

## 四、切块策略（RAG 里最影响效果的一环）

对应文件：`fin_rag/chunking.py`

实现了三种，可以通过环境变量切换，**能对比才叫工程，不能对比只能算玄学**：

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| `fixed` | 定长字符滑窗 + overlap | 简单、块大小均匀 | 会把句子切断 |
| `semantic`（默认） | 按句子贪心装箱，不切断句子 | 语义完整 | 块大小不均 |
| `small_to_big` | **索引小块（句子），返回大块（父段落）** | 匹配精确 + 上下文充足 | 实现复杂，要去重 |

`small_to_big` 值得单独理解：**检索时希望块小**（小块语义单一，匹配更准），
**给模型时希望块大**（上下文够，才答得完整）。这两个需求矛盾，
解法就是"索引的单位"和"返回的单位"分开——`Chunk.text` 用于索引，`Chunk.context` 用于喂模型。

副作用：多个子块共享同一个父段落，直接拼 prompt 会重复三遍浪费 token。
所以有 `dedupe_context()` 和 `build_context()` 里的去重。

**还有一个关键设计：`index_text`（上下文标题前缀）。** 这是本项目最大的一次提升，
详见 `03-踩坑记录.md` 坑 1，务必读。

## 五、合规层：金融 RAG 和普通 RAG 的真正区别

对应文件：`fin_rag/compliance.py`

普通知识库答错了是体验问题；金融知识库答"这只基金你该买"是**监管问题**。

三档处理，不是简单的"允许/拒绝"：

| 输入类型 | verdict | 行为 |
|---|---|---|
| 下单、转账、内幕消息 | `refuse` | 直接拒答，不检索 |
| "该不该买"、"明天涨吗" | `allow_with_disclaimer` | **照答事实 + 挂免责声明**，但不给建议 |
| "管理费多少" | `allow` | 正常答 |

中间那档是设计上的关键：**用户问"该不该买"，背后往往是想了解产品，
一律拒答体验极差。正确做法是给他事实（费率、回撤、风险等级），
但不替他做决定。** 这个思路在真实合规要求里叫"信息服务 vs 投资建议"的边界。

### 两道防线，不只靠 prompt

1. **入口**：`check_query()` 正则分类，决定路由。
2. **出口**：`sanitise_answer()` 正则清洗生成结果，`保证收益`/`稳赚不赔`/`建议买入` 都会被替换。

为什么出口还要拦一道：**prompt 是"请求"，不是"控制"。** 你在 prompt 里写"不许说保证收益"，
模型大概率听，但不保证。真要卡死，必须有代码级的后置过滤。这句话面试很好用。

另外注意顺序：先查"违规动作"再查"投资建议"。
问"这只基金该不该买，帮我下单"必须走拒答，不能因为先匹配到"该不该买"就降级成挂免责声明。
（测试：`test_action_check_precedes_advice_check`）

## 六、评估：怎么证明"我改的东西真的有用"

对应文件：`fin_rag/evaluation.py`、`scripts/eval.py`

四个指标，都能离线算、不需要大模型当裁判（所以能进 CI）：

| 指标 | 含义 | 怎么算 |
|---|---|---|
| `hit_rate` | 召回里有没有正确文档 | 命中数 / 总数 |
| `mrr` | 第一个正确文档排多靠前 | 平均 1/(首个正确的排名) |
| `context_precision` | 召回的块里有多少是相关的 | 相关块 / 召回块 |
| `groundedness` | 答案有多少能追溯到原文 | 答案 token 在上下文里的占比 |

`groundedness` 是**幻觉的代理指标**：如果答案里出现了原文没有的内容，这个值就掉。
本项目 mock 下恒为 1.0（因为 mock 只会抄原文句子），接真模型后会低于 1，那才是真正有意义的监控值。

`scripts/eval.py --ablate` 会跑四种配置对比。**做过消融实验**这件事本身就是加分项，
它证明你不是"把技巧堆上去然后声称有效"。

## 七、工程层：让它像个能上线的服务

对应文件：`fin_rag/api.py`

### SSE 流式，且引用先于 token

```
event: citations   ← 先发，UI 立刻能渲染"参考来源"
event: token       ← 再逐字发答案
event: disclaimer
event: done
```

为什么这个顺序：RAG 一次响应要好几秒，用户看着转圈会走。
先把来源发出去，用户马上有东西看；而且客户端不用等流结束才知道答案依据什么。

### 降级设计

| 故障 | 行为 |
|---|---|
| 模型 API 挂 | 返回"生成服务不可用 + 检索到的来源"，不返回 500 |
| HyDE 失败 | 回退用原问题检索 |
| 检索为空 | 拒答，不让模型编 |

### 可观测：trace 字段

每个节点往 `trace` 里追加一条，响应里带回来：

```json
"trace": ["compliance:allow", "expand:hyde(102chars)", "retrieve:12", "rerank:12->4", "generate:118chars"]
```

排查线上问题时，看一眼 trace 就知道请求走了哪条路、每一步剩多少候选。
这比"加日志然后去翻日志"轻量得多，也是 LangSmith 那类可观测工具的简化版思路。

## 八、必须能坦白说出来的局限

面试官问"这个项目有什么不足"，答不出来的人显得没深度。这些是真实局限：

1. **hashing embedder 不是语义模型**，处理同义改写远不如 BGE，只是为了离线可跑。
2. **重排器不是真 cross-encoder**，`TorchReranker` 才是，但 CI 里没跑（要下模型）。
3. **HyDE 在离线配置下测不出收益**（见踩坑记录坑 5）。
4. **没有鉴权、限流、多租户隔离**，必须挂在网关后面。
5. **索引在内存里**，启动时重建，没有增量更新，生产要换持久化向量库。
6. **只支持 .md/.txt**，PDF/OCR 解析没做（大纲里的 MinerU 那部分是可以继续加的方向）。
